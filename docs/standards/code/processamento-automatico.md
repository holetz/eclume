# Automatic processing — pipeline, fields, agenda types and summary by type

After upload, each recording goes through a chain of steps without anyone asking: the audio is
received, preprocessed and transcribed by the GPU worker; the speakers are checked (and, if the account
requires it, the recording waits for the owner to name them); the agenda type is detected, the fields are
filled and the summary is generated by the CPU worker. The routes follow [contract v1](../api/contrato-v1.md),
persistence and isolation follow the [server core](server-nucleo.md), the providers and the
`summarize` job follow [agents](server-agentes.md), and preprocessing follows the
[job contract](../api/jobs-transcricao.md).

## The pipeline per revision

`pipeline_steps` stores one row per (recording, revision, step). The revision is the transcription
job's (`transcription_jobs.revision`): retranscribing opens a new revision and redoes the chain.

| Step | Who writes it |
|---|---|
| `received` | `recordings.insert_job`, when creating the job (upload, retranscription, retry); `failed` with a mismatched hash |
| `preprocessing` | ingestion, from the GPU worker's `engine_info.preprocess`; cancellation during download or preprocessing (`skipped`, `cancelled`) |
| `transcription` | ingestion (`done`), the failure and the reaper (`failed`, with the job's error), cancellation (`skipped`, `cancelled`) |
| `speakers` | ingestion (`done` or `waiting`), the resume on naming or merging (`done`), `continue` and turning the preference off (`skipped`) — see [Speaker naming](#speaker-naming) |
| `agenda_type` | the `detect_agenda_type` job |
| `fields` | the `fill_fields` job |
| `summary` | the automatic summary: `active` when opened, `done`/`failed` when `summarize` finishes |

- **States:** `pending`, `active`, `done`, `failed`, `skipped` and `waiting` (those of the Design System's
  `.pipeline` component); `waiting` belongs only to the `speakers` step. Skipped or failed, the step says why: `detail.reason` or
  `error_code`/`error_message`. The reason codes today: `no_provider` (no agent for the step),
  `no_auto_fields`, `no_types`, `set_by_user`, `no_agenda_type`, `before_pipeline` (a recording
  older than the pipeline, migration 012), `worker_without_preprocess` (the GPU worker does no
  preprocessing), `summary_deleted` (the step's summary was deleted), `cancelled` (the
  transcription cancelled by the owner at this step) and, on the `speakers` step, `unnamed_speakers` (in
  `waiting`), `continued_by_user` and `naming_not_required`.
- **A new reason code requires text.** Every code gets text in `MOTIVOS` of the shared
  vocabulary (`web/src/lib/vocabulario.js`, copied in the desktop and the phone app, see
  [frontend-web.md](frontend-web.md)): `vocabulario.test.ts` reads the server's and the migrations'
  `"reason": ...`, `skip = ...` and `reason=...` and fails on a code without text. On screen, a code still
  unknown appears raw.
- `pipeline.set_step` upserts by `(recording_id, revision, step)`: `active` marks the start, a
  final state marks the end and keeps the start; `duration_ms` is a generated column.
- **`Recording.pipeline`** is the seven steps of the highest revision, in order; with no row, `pending`.
  While the GPU worker reports progress, preprocessing (the `preprocess` stage) or
  transcription (the others) comes out `active`.
- **The chain never stops on an agent failure:** fields, type and summary write their own step and
  enqueue the next. They only stop when the recording was deleted or the revision is no longer the current one; the
  only deliberate stop is the wait for the speakers' names, before the type.
- Migration `012` filled in the history: `received` and `transcription` from the jobs; preprocessing,
  fields and type `skipped` with `before_pipeline`; summary `done` when there was an automatic summary.

## Speaker naming

The account can require every speaker to have a person before the agent chain (holetz/eclume#144):
recordings with new voices stay stopped until the owner says who is who.

- **Account preference:** `users.require_speaker_naming` (migration 030, default `false`), at
  `GET /me/speaker-naming` (session or PAT `recordings:read`; carries `required` and `waiting_count`) and
  `PATCH` (session only). Turning it on applies to the next ingestions.
- **The gate lives in ingestion** (`speaker_naming.gate`), in the same transaction, after the restoration
  of the links and the assignment by voice: with the preference on and some speaker without `person_id`
  with at least 10 s of speech (`MIN_REQUIRED_TALK_MS`, the floor of the voice comparison), the
  `speakers` step stays `waiting` with `detail = {"reason": "unnamed_speakers", "unnamed": N}`, and
  `ingest_transcript` does not enqueue `detect_agenda_type`. Without the gate, the step ends `done`. An automatic
  link by voice counts as named; a label without a person does not.
- **`waiting` marks start and end** like a final state (`STOPPED` in `pipeline.py`), but is not in
  `FINISHED`. On leaving the wait, the end is rewritten and the start kept: `duration_ms` measures the
  wait. Naming a speaker without clearing the gap only updates `detail.unnamed`, without touching the instant
  (the outcome notices compare `finished_at`).
- **The exit is the server's.** The speaker's `PATCH` with `person_id` and the merge call
  `release_if_named`: with nobody missing in the current revision, the step ends `done` and the route enqueues
  `detect_agenda_type` after the commit (`Queue.enqueue_step`, the same `_job_id`). `POST
  /recordings/{id}/continue` (`recordings:write`) releases with `skipped`/`continued_by_user`; outside the
  wait, 409 `conflict`. Turning the preference off releases every stopped recording of the account
  (`skipped`/`naming_not_required`) in the same transaction and enqueues each one.
- **The resume does not relaunch** the revision with `speakers` in `waiting`; if the enqueuing after the
  exit is lost, the cron relaunches it, because the step has already finished.
- **API:** `Recording.awaiting` (`"speakers"` or `null`) and `GET /recordings?awaiting=speakers`
  (the `speakers` step in `waiting` on the highest job revision). The MCP repeats both.
- Migration 030 wrote `speakers` `done` on every revision already transcribed.

## Fields and the value origin

`fields` belongs to the user (`owner_id`, owner RLS). Every account has the built-in **title** (`text`) and
**tags** (`list`), with the default rule, which cannot be removed or change type (409 `builtin_field`, 422). The
title does not appear in "Campos personalizados" (custom fields) and its rule no longer applies: the subject follows the rule
of the recording's type (see [Agenda types](#agenda-types)); migration `021` made it always
automatic. The
others are `text`, `list` or `choice` (with `options`), each with its rule (`instructions`) and
`auto_fill`. The `key` is the slug of the name, unique per account and without the placeholders `assunto`, `data` and
`tipo`; it does not change when the name changes.

- `field_values` stores the value (`text`/`choice` → string, `list` → array, `null` = nothing
  found) and the **origin**: `auto` (the agent), `edited` (the user wrote it) or `accepted` (the
  user accepted the automatic one). **`edited` and `accepted` are never overwritten** by an
  automatic fill.
- Title and tags remain in `recordings.title`/`tags`, which search and the library read. Every
  write goes through `fields.set_value`, which updates both tables together. `PATCH /recordings`
  with a title or tags and an upload with an explicit title or tags become `edited`; the file name
  has no origin, and the automatic one replaces it.
- Changing a field's `kind` discards its values.
- **Ceilings:** field rule, `identify` and `summary_instructions` up to 4000 characters; a value written
  by the user up to 300 characters (text) or 50 items of up to 300 (list); a tag, written or
  automatic, up to 64, like a type's default tags.

## Tag registry

`tags` is the user's registry (`owner_id`, owner RLS): name (up to 64, unique ignoring accents and
case), description ("quando usar" (when to use), up to 4000) and origin (`user`, or `auto` when the agent created it).
`recordings.tags` remains the recordings' value; the registry sits beside it. Migration `023`
registered the tags already used on recordings and in the types' default tags, with the most used spelling of
each name, and moved the recordings to that spelling; seeding a new account registers the default tags
of the types it gets.

- **A tag written by the user is registered on its own** (`tags.adopt`): the `edited`/`accepted` value of the
  built-in Tags (edit, upload, field) and a type's default tags (create and edit) take the registry's
  spelling, and what is missing is registered with origin `user`.
- **Rename, merge and delete** (`PATCH /tags/{id}`, `POST /tags/{id}/merge`, `DELETE`) also change
  `recordings.tags` and `agenda_types.default_tags`, without repeats and in the same order
  (`tags.replace_everywhere`), and bump the `updated_at` of the recordings and the transcripts. A name already
  registered is 409 `tag_exists`.
- **Mode** (`users.tag_mode`, `GET/PATCH /me/tag-assignment`): `fixed` (default) — the agent only uses
  registry tags; `auto` — it may create up to `users.tag_new_limit` (1 to 5, default 1) new tags per
  recording, always preferring to reuse, while the registry has fewer than `MAX_CATALOG` (200). The
  automatic switch and the general rule are those of the built-in Tags (`auto_fill`, `instructions`).

## Agenda types

`agenda_types` belongs to the user: name, `title_pattern`, `title_instructions` ("como escrever o
assunto" (how to write the subject)), `identify` ("como identificar" (how to identify)), `default_tags`, `summary_instructions` and `position`.
They replace the summary templates: migration `009` converted each template into its owner's type, with the
same id.

- **Fallback type** (`is_fallback`, `fallback` in the API; "Geral", with the "Padrão" badge on screen):
  one per account (partial unique index), created by migration `021` and by
  `eclume_seed_fallback_type(user)`, which seeding a new account calls after the built-ins. It is born
  with `{assunto}` as the pattern, the account's built-in title rule as the subject rule and
  generic summary instructions; "Geral" already taken becomes "Geral (padrão)". It cannot be removed (409
  `fallback_agenda_type`) and does not compete in detection. Deleting another type moves its recordings
  to the fallback one, with origin `auto`.
- **Subject rule** (`title_instructions`): the rule the agent follows for the automatic title
  (`{assunto}`). Empty, the fallback type's applies; also empty, the factory one
  (`DEFAULT_TITLE_RULE`). The admin also writes it in the default types they distribute.

- **The admin's default types** (`default_agenda_types`, platform-wide, admin session only): those
  marked `include_for_new_users` are copied into each new account by
  `eclume_seed_user_defaults(user)`, which `accounts.create_user` calls at sign-up and which also creates
  the built-in fields. Changing a default does not touch the copies accounts already have.
- **Title pattern:** placeholders `{assunto}` (the automatic title; without it, the title from before the
  first pattern, kept in `recordings.subject`, to reapply without nesting), `{data}` (`dd/mm/aaaa` of
  `recorded_at`), `{tipo}` and `{<key do campo>}`. The pattern is cut at the separators (` · `, ` - `,
  ` | `, dashes); a part that ends up empty goes away together with its separator.
- **Applying the type** (`agenda_types.apply_type`): writes `agenda_type_id` and the origin (`auto` or
  `edited`), replaces the title with the pattern if the title is not `edited`/`accepted`, and adds the default
  tags to the automatic ones (the user's stay as they are). Detection applies it without the title
  (`render=False`); `fill_fields` rebuilds it at the end (`refresh_title`), with the new subject, and adds
  the default tags again to the ones it has just written.
- **Switching the type by hand** (`PATCH /recordings/{id}` with `agenda_type_id`): origin `edited`, title
  and tags reapplied and, on a transcribed recording, a new automatic summary with the `summary` step
  redone — if there is not yet an automatic one of the same revision for that type. `null` removes the type and
  returns the choice to detection.

## Resume

A step that never reached the queue (Redis flickered, or the worker stopped between the commit and the
enqueuing) comes back on its own. The `resume_pipelines` cron (`resume.py`, every 5 min, `unique`, on the
`eclume:default` worker) rereads the database and relaunches by the deterministic `_job_id`, which arq
deduplicates; there is no outbox:

- **The chain**, only on the current revision with the transcription job `succeeded` more than 5 min ago and the
  `speakers` step out of `waiting`: agenda type without a row → `detect_agenda_type`; type final and fields without a row → `fill_fields`; fields
  final and summary without a row → the automatic summary (`start_auto_summary` and `summarize`), without redoing
  the fields.
- **The summaries** `queued`/`running` for more than 5 min: vanished from arq → re-enqueued; finished in
  arq with the summary still open → `failed` (`internal_error`) and the step closed. What arq still
  knows (queued, deferred, running) is never touched — the summary waiting for the GPU stays intact.
- Up to 50 relaunches per pass, oldest first, each one in a `log.warning`.

## The per-agent jobs

The agent worker (`eclume:agents`, holetz/eclume#96) chains `ingest_transcript → detect_agenda_type → fill_fields → summarize`, with
`_job_id = "{job}:{recording_id}:{revision}"`; ingestion, on the `eclume:default` worker, opens the
chain by enqueuing on `eclume:agents`. Only the ingestion that wrote the transcript opens the chain:
a job already failed (by the reaper) or a repeated ingestion does not enqueue `detect_agenda_type`. The type comes
before the fields because the title's subject follows the type's rule. Each job resolves the provider by purpose
(`provider_for`) and calls the agent through `summaries.call_agent_step`, which applies the retries of
`summarize` (3 attempts, 30 s and 120 s; `gpu_busy` postpones without spending an attempt) and counts the
attempts in the step's `detail.attempts`. A definitive failure leaves the step `failed`, and the chain
goes on; so does an unexpected failure outside the agent call (`internal_error`, in
`worker._run_step`).

### `fill_fields`

- Eligible fields: those with `auto_fill` whose value is not `edited`/`accepted`. None → `skipped`
  (`no_auto_fields`); no `fields` provider → `skipped` (`no_provider`).
- The title goes with the subject rule of the recording's type (`agenda_types.title_rule`), not with the
  built-in field's.
- **Context and collections** (`fields.recording_context`): the prompt gets the recording's agenda type
  (`## Tipo de agenda da gravação`), the identified participants (the people linked to the
  speakers, with company, department, role and person tags) and, when there are any, the auto collections with a
  rule (`auto_assign` and `instructions`) as `C1..Cn` (`- C1: Nome — regra`), with `COLLECTIONS_TASK`
  and the key `"colecoes": ["C1", …]` in the format. An index outside the list is ignored; across sections, the union.
  Collections alone, with no eligible fields, also call the agent.
- **Writing the collections** (`fields.apply_collections`), by the origin `recordings.collections_origin`:
  `edited` (the user changed them through `PATCH`) → nothing changes, and the collections do not even go to the prompt; `auto` → the
  chosen ones replace the previous automatic ones, and the others stay; null (coming from the upload, or still
  without a choice) → only adds. If it chose any, the origin becomes `auto`. The step stores `collections`.
- At the end — filled, skipped or failed —, `refresh_title` rebuilds the title from the type's pattern. When it
  finishes, the worker opens the automatic summary.
- One call for all fields (`agents/extraction.py`), (never one per field),
  with the `system` `SHARED_SYSTEM`, the same as the summary's, and the transcript in `<transcricao>` in the
  `context` (the cacheable block, identical to the summary's: `Provider.complete` in
  [server-agentes](server-agentes.md)). The rules come in the prompt, after the transcript, starting
  with `FIELDS_SYSTEM`: "Tarefa: preencher campos da gravação transcrita. Para cada campo, siga a
  regra do usuário; sem a informação na conversa, devolva null. Responda só com um objeto JSON,
  sem texto fora dele." (Task: fill in the fields of the transcribed recording. For each field, follow the
  user's rule; without the information in the conversation, return null. Reply only with a JSON object,
  with no text outside it.)
- The prompt lists `- key (tipo[, opções: a | b]): regra`, the tag registry (`## Tags
  cadastradas`, `- nome — descrição`, up to 200, with the mode's rule: "use só tags desta lista" (use only tags from this list) or
  "prefira sempre uma tag desta lista… no máximo N nova(s) por gravação" (always prefer a tag from this list… at most N new per recording)) when the built-in Tags is
  eligible, and the expected format.
- **The agent's tags** (`tags.resolve`): each proposed tag is matched against the registry by
  `tags.canonical` (ignoring accents and case, hyphens and spaces unified, Portuguese plural turned
  singular) and takes the registry's spelling; those that do not match only stay in `auto` mode, up to the
  per-recording limit and the room left in the registry, and enter it with origin `auto`. In `fixed` mode, they
  are dropped.
- A transcript larger than the window: one call per section (`split_sections`) and the merge — text and
  choice, the most frequent non-null value (on a tie, the first); list, the union without repeats.
- Validation: a choice outside the options → `null`; a list of strings, up to 10; text up to 300
  characters. JSON that does not parse → `provider_bad_output`, retryable.
- Writes with origin `auto`, rechecking eligibility: what the user wrote while the agent
  worked stays.

### `detect_agenda_type`

- A type chosen by the user (`edited`) → `skipped` (`set_by_user`), and the summary uses that type.
  Only the fallback type → `no_types`; no `agenda_detection` provider → `no_provider`.
- The types, **without the fallback one**, become `T1..Tn` (name and how to identify) and the transcript goes only
  up to the window budget, from the start (Ollama has 8 k, and the subject shows up early).
  `DETECT_SYSTEM` asks for the type that best describes the recording, or `null` when none fits, and only the
  JSON `{"tipo": "T2" ou null, "confianca": 0.0-1.0, "motivo": "uma frase"}`. A `tipo` outside the
  list, or the key missing, is `provider_bad_output`.
- **Fallback:** `tipo: null` or a confidence below `MIN_CONFIDENCE` (0.6) applies the fallback
  type; the step stores the applied type, `fallback`, the candidate (`candidate_name`), the confidence
  and the reason. Skipped or failed, the worker applies the fallback one to the recording without a type (`ensure_type`,
  which does not stop the chain if it fails): the summary always has a type.
- The result is applied with origin `auto`, without the title, which waits for the fields.

### The automatic summary by type

`summaries.start_auto_summary`, called by the worker at the end of `fill_fields`, opens the summary
`trigger: automatic` with the instructions of the recording's type and the `summaries` provider, and marks the `summary` step `active` with the `summary_id`. No type
→ `skipped` (`no_agenda_type`); no provider → `no_provider`. When the automatic one of the same
revision and the same type already exists, nothing is created. `summarize` closes the step; a summary deleted before
generating closes it `skipped` (`summary_deleted`). A single-call summary reads the transcript like
`fill_fields` (same `system` and same `context`), so the provider's prompt cache serves both
steps and the `fill_fields` retry.

## Retranscription

The new revision redoes the chain: `auto` values and an `auto` type are recomputed; `edited` and `accepted`
stay.

## Previews

"Testar numa gravação" (test on a recording) (`POST /fields/preview`) and "Pré-visualizar numa gravação" (preview on a recording)
(`POST /agenda-types/preview`) run the `run_preview` job over a draft, without writing anything to the
database: the state lives in Redis (`eclume:preview:{id}`, with `owner_id`, `kind`, `status` and `result`)
for 1 h, and `GET /previews/{id}` from another account is 404. Each account has at most 3 open (queued
or running, in `eclume:preview:open:{owner_id}`); the fourth is 429 `rate_limited`.

- `field_rule` runs `FIELDS_SYSTEM` with only the draft field, on up to 3 transcribed recordings (the
  ones given, or the user's 3 most recent).
- `agenda_type` runs, on one recording, the detection with the draft in place of the saved type it edits
  (`agenda_type_id`, or the one with the same name), the title and the tags it would apply and the summary with the
  draft's instructions. The fallback rule applies the same way: `fallback` says the default type would stay;
  a draft of the fallback type itself does not compete and is the one that stays when none fits.

## Tests

`FakeAgents` (`eclume_server_testing/fakes.py`) recognizes the purpose by the system prompt
or, for fields, by the rules in the prompt (`FIELDS_SYSTEM`, `DETECT_SYSTEM`, summary) and has a queue of replies per purpose
(`replies`) and of errors per purpose (`failures`); with no scripted reply, the fields come out empty, detection picks `T1` and the summary is
deterministic Markdown. No test calls an LLM. `server/tests/test_processing.py` proves the chain
with the real CPU worker.
