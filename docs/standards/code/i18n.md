# Internationalization (i18n)

eclume speaks two **product locales**: `en` (the default) and `pt-BR`. The product locale decides the
language a person reads: the UI, the error messages the client shows, and what the agents write
(summaries, field values, chat and Agent answers). It is **not** the language of the audio: the ASR
language stays `pt-BR` per recording (`Recording.language`) and does not follow the account locale.
Terms are mapped in the [glossary](../../glossary.md).

## The account locale

- **Where it lives:** `users.locale` (migration `035_account_locale.sql`), `en`, `pt-BR` or `null`
  (the account never chose). The migration backfilled every account that existed before it to
  `pt-BR`, because all of them were Portuguese speakers.
- **Signup** stores the best supported match of the browser's `Accept-Language`, or `null` when
  none matches.
- **Read and write:** `GET`/`PATCH /api/v1/me/locale` (contract 2.30.0), `{locale, effective,
  default, supported}`; any valid credential reads it (no scope, like `/me`), only the browser
  session writes it.
  `User.locale` and `AdminUser.locale` show the stored value.
- **Resolution** (`eclume_server.locale`):
  - a **request** uses the account locale, then `Accept-Language`, then `en` (`resolve`);
  - a **job** has no request: it uses the owner's account locale, else `en` (`job_locale`).
- Tags are normalized by `normalize`: `pt`, `pt-br` and `pt_BR` become `pt-BR`, `en-US` becomes
  `en`; anything else is unsupported.

## API errors

- The **`code`** of a problem (`application/problem+json`) is the localization key. Clients map
  `code` to their own text in the person's locale and treat an unknown `code` as a generic error.
- **`title` and `detail` are English** and informative only, for logs, `curl` and integrators. Never
  write a Portuguese `title` or `detail`, and never make a client parse them.
- `problems.CODES` is the server's catalog: every code with its English title. The contract's
  `ProblemCode` enum lists the same set; `server/tests/test_problem_codes.py` proves that every code
  the server raises is in `CODES`, that `CODES` equals `ProblemCode`, and that no literal `detail`
  is Portuguese.
- **A new code** goes into `problems.CODES` and into `ProblemCode` in the same change (a contract
  minor, per [contrato-v1.md](../api/contrato-v1.md)), and the clients add its text.
- Job failure messages (`error_message`) are still Portuguese text and are not keyed yet.

## Generation

- Prompts are **English** (`agents/prompting.py`, `extraction.py`, `chat.py`, `base_chat.py`,
  `agent.py`, `agent_tools.py`).
- The language of the output comes from the **owner's locale**, through one line appended after the
  transcript and the task (`prompting.output_language`):
  - `en`: `Write the output in English.`
  - `pt-BR`: `Write the output in Brazilian Portuguese (pt-BR).`
- The line goes last, so the cached prefix (system and transcript) is the same in every locale. The
  summary job, previews, field filling, the summary chat, the base chat and the Agent pass the
  locale; the map-reduce notes of long transcripts stay English and only the final document follows
  the locale.
- User-authored text (agenda type instructions, field rules, skills) is used as written, in any
  language.

## The web app

- **Library and catalogs.** `react-i18next` over `i18next`, set up in `web/src/i18n/index.ts`.
  Catalogs are TS modules, one file per namespace and locale: `src/i18n/en/<ns>.ts` exports an
  `as const` object, and `src/i18n/pt-BR/<ns>.ts` is typed `Catalog<typeof en>` (`locale.ts`), so a
  missing or extra key fails `tsc`. `i18next.d.ts` declares `CustomTypeOptions`, so `t('ns:key')` is
  type-checked. A new namespace adds its two files and one entry to each locale's registry
  (`en/index.ts`, `pt-BR/index.ts`).
- **Only the active locale loads.** Each locale's registry is its own chunk (about 23 KB gzip for `en`, 24 KB for `pt-BR`), out of
  the initial JS. `startI18n` picks the starting locale before the first render: the one this browser
  last showed (`localStorage` `eclume-locale`, written by `setLocale`), else the browser language,
  else `en`. It loads that chunk, and `main.tsx` mounts the app after it, so the first frame is
  already in that language. `setLocale` loads the other locale on the first switch. The initial-JS
  ceiling (`web/bundle-budget.json`) therefore grows with the code, not with the text.
- **Namespaces** follow the areas: `common` (Save, Cancel, Loading…), `errors` (problem codes),
  `shell` (navigation, header, help drawer, route errors, notifications), `shared` (the pipeline
  vocabulary, recording states, markers, months, language picker), `auth`, `account`, `connect`,
  `tokens`, `environment`, `desktop`, `library`, `transcript` (the recording page: frame, summary,
  fields, speakers, chat), `import`, `search`, `people`, `organize` (custom fields and agenda types),
  `collections`, `tags`, `admin` (the administration panel: frame, sections and option tables),
  `agent` (the Agent: conversations, action cards and skills), `automation` (the automatic
  processing overview) and `help` (the help center chrome: center, drawer, search, article frame,
  topic and help page names). All of them join the locale's chunk; no namespace loads per route. The
  registries key the import catalog as `import: importCatalog`, since `import` is not a variable name.
- **The pipeline vocabulary** (step names and progress, step states, skip reasons, device states,
  the waiting phrase) lives in the `shared` catalog and is read through the helpers of
  `shared/format.ts` (`stepName`, `stepStateLabel`, `reasonText`, `deviceStateLabel`,
  `waitingPhrase`). `lib/vocabulario.js` stays as it is, because the desktop and the phone copy it
  byte for byte; `src/i18n/vocabulary.test.ts` keeps the pt-BR catalog equal to it and the en
  catalog on the same keys, so the three clients cannot drift.
- **Resolution.** `LocaleSync` (`sync.tsx`, in the providers) follows the `/me` query without
  fetching it: the account's `user.locale` when the session has one, else the browser language
  (`navigator.languages`, normalized like the server's `normalize`), else `en`. Public pages (login,
  signup, pairing) and the admin panel therefore read the browser language. It switches only on a
  real change. `setLocale` changes the language in place, with no reload, and sets
  `<html lang>`.
- **Switcher.** My settings › Account (`/config/conta`), the `LocaleSection`: the browser's language
  (`locale: null`) or one of the supported locales, saved with `PATCH /me/locale` and applied at
  once.
- **Problem codes.** `api/problem.ts` shows `errors:<code>` for the problem's `code`. The `errors`
  catalog is typed `Record<ProblemCode, string>`, and `problem.test.ts` reads the contract's enum,
  so a code without text fails. An unknown code gets the message of its HTTP status, else a generic
  one. The client never shows `title` or `detail`.
- **Formats.** Dates, numbers and language names use `Intl` keyed by `activeLocale()` (formatters
  cached per locale in `shared/format.ts`), so they follow a switch. Plurals use i18next's `_one`
  and `_other` keys; `_zero` is added where pt-BR must say "0 pessoas" (Intl counts 0 as singular in
  Portuguese). A catalog never spells out the other categories: `completePlurals` (`plurals.ts`)
  fills every `Intl.PluralRules` category of the locale from the set's `_other` text when a bundle
  is added, so pt-BR's `many` (exact millions) reads as text instead of the bare key.
  `plurals.test.ts` walks every loaded catalog of each locale and fails on a set missing a category.
- **Literal-string check.** `src/test/literalStrings.test.ts` parses the directories in `COVERED`
  with the TypeScript compiler and fails on a JSX text with letters, a literal in a visible
  attribute (`aria-label`, `title`, `placeholder`…) or in a text prop (`label`, `title`, `hint`,
  `message`…). A brand or a key name stays literal with an `i18n-ignore` comment on the line above.
  Each extracted area adds its directory to `COVERED`.
- **Tests.** Unit tests run in pt-BR (`test-setup.ts` pins the language and `navigator.languages`),
  so the existing assertions hold. Each extracted area also asserts its screen in `en`, through an
  account with `locale: 'en'` or `setLocale('en')`. `e2e/locale.spec.ts` logs in under each browser
  language, rewrites `/me` and `/me/locale` to play the account locale, and switches with no reload.
- **Option tables.** A module-level table of labels (`features/admin/labels.ts`, the help `TOPICS`
  and `HELP_PAGES`) keeps its shape and reads its text through getters on `i18n.t`, so a value is
  resolved when used and follows a switch; brand and contract names (WhisperX, Ollama, RNNoise…)
  stay literal.
- **Still pt-BR.** The help articles and the frequently asked questions (`features/help/articles/`,
  `perguntas.md`), and the route paths.

## The desktop app

- **One resolver, in Rust.** `desktop/src-tauri/src/i18n.rs` holds `Locale` (`en`, `pt-BR`),
  `normalize` (the same rules as the server's and the web's) and `resolve`: the desktop's own choice
  (`config.locale`, `null` = Automatic), then the account's `user.locale` (cached as
  `config.account_locale`, read from `GET /api/v1/me` after sign-in, at app start and on Test
  connection, and dropped when the account signed out while the request was in flight), then the
  system language (`config.system_locale`: the first supported entry of `navigator.languages`, or
  the first entry when none is supported, so a French system resolves to `en`, reported through
  `report_system_locale`; before the first report, the first set of `LC_ALL`, `LC_MESSAGES` and
  `LANG` on Unix, so `LC_ALL=C` overrides `LANG`), then `en`. The `status` payload carries the resolved `locale`
  and the `locale_choice`, so the window and the tray never disagree.
- **Switcher.** Settings › General: Automatic (the account, then the system), English, Português
  (Brasil), saved locally with `set_locale` and applied at once to the window and the tray. It never
  writes the account locale: `PATCH /me/locale` is session-only, and the desktop holds a device
  credential.
- **Rust catalog.** `i18n.rs` `Texts`, with one `const` per locale (`EN`, `PT_BR`), so a missing
  string fails to compile; placeholders are `{name}`, filled by `fill`. The tray menu (rebuilt when
  the locale changes), the notifications, the tray's Recent labels and the status label read it.
- **Window catalogs.** `desktop/ui/js/i18n.js` (`t`, plurals through `Intl.PluralRules`,
  `setLocale`, `onLocaleChange`) over `desktop/ui/js/locales/en.js` and `pt-BR.js`, with the same key
  tree, keyed by view. `index.html` carries English text with `data-i18n`, `data-i18n-aria-label`,
  `data-i18n-title`, `data-i18n-placeholder` or `data-i18n-alt`; `<html lang>` follows. The first
  frame uses `localStorage` `eclume-locale`, else the browser language, else `en`, then follows
  `status.locale` with no reload. Shortcut labels and registration problems come from the catalog
  by `action` and `registration` id, not from Rust's labels.
- **Pipeline vocabulary.** `ui/js/vocabulario.js` stays a byte copy of the web's; `ui/js/vocabulary.js`
  serves it in pt-BR and the en catalog's `vocabulary` keys (the web's `shared` English) in en.
- **Checks.** `desktop/ui-tests/locale.spec.ts` renders both locales, switches with no reload and
  compares the catalogs' keys; the other UI tests run in pt-BR. `ui_assets.rs` fails on a Portuguese
  literal anywhere in `desktop/ui` outside `js/locales/pt-BR.js` and `js/vocabulario.js`. The Rust
  text tests assert both locales.
- **Still pt-BR.** The error and notice text Rust sends to the window (`bail!`, `context`,
  `state.notice`, `sync_notice`) and the shortcut names registered with GNOME and the portal. The help
  center opens the web's `/ajuda`, in the web's own locale.

## The mobile app

- **One resolver, in the Rust core.** `mobile/crates/core/src/locale.rs` holds `Locale` (`en`,
  `pt-BR`), `normalize` (the server's rules: the base language decides) and `resolve`: the account's
  `users.locale` (read from `GET /me/locale` with the account's types and language during a sync
  pass and cached as the config's `locale`; a server older than 2.30.0 keeps the cache), then the device language (`device_locale`, reported by
  the UI through `report_device_locale` at start and on `languagechange`: the first supported entry
  of `navigator.languages`, else the first entry), then `en`. `AppState.locale` carries the result,
  so the UI, the notification and the worker never disagree. The phone has no switcher of its own:
  the account's choice is made on the web.
- **Core texts.** What the core writes for display follows the resolved locale: the space and time
  estimates (`estimates::about`, `about 9 h` / `cerca de 9 h`) and the stop reasons
  (`StopReason::text`). Its error texts (`bail!`, `context`, `ultimo_erro`) are still pt-BR.
- **UI catalogs.** `mobile/ui/src/i18n/index.ts` (`t`, `useT`, `setLocale`, `formatLocale`, plurals
  as `_zero`/`_one`/`_other`, `{name}` placeholders) over `en.ts` (`as const`, the source) and
  `pt-BR.ts` (typed `Catalog<typeof en>`, so a missing or extra key fails to compile), keyed by
  screen. No i18n dependency: it is a typed module. The first frame uses the device language
  (`deviceLocale`), then follows `state.locale` with no reload; `<html lang>` follows. Dates and
  sizes go through `app/formats.ts` in the active locale.
- **Pipeline vocabulary.** `ui/src/app/vocabulario.js` stays a byte copy of the web's;
  `ui/src/i18n/vocabulary.ts` serves it in pt-BR and the en catalog's `vocabulary` keys in en.
- **Android resources.** The recorder plugin's notification, action, channel and sync texts live in
  `mobile/plugins/gravador/android/src/main/res/values/strings.xml` (English) and
  `values-pt-rBR/strings.xml`, read through `Localized.kt` (`Strings`, on a context set to the
  core's `locale`: the service from `AppState`, the worker from the probe's `locale`; the watchdog,
  with no core, from the device). Counts take `_one` for 1 and `_other` otherwise. The channel ids
  and the shortcut id stay as registered; the channel names follow the locale. The app's
  record-now shortcut labels are English in `values/` and pt-BR in `values-pt-rBR/`; the brand
  strings are `translatable="false"`.
- **Checks.** `ui/src/test/literalStrings.test.ts` fails on Portuguese text anywhere in
  `mobile/ui/src` outside `i18n/pt-BR.ts`, the vocabulary copy, the fake bridge and the tests. The
  screen tests run in pt-BR (`test-setup.ts`) and each screen group has an English test. The JVM
  tests read the real `strings.xml` files, assert both locales and check that both have the same keys
  and placeholders and that `Localized.IDS` names every key. The Rust tests assert the resolver and
  the core texts in both locales.

## For a new artifact

- Code, comments, identifiers, docs, commits and specs are written in English.
- Translating an identifier never renames what it serializes. JSON and serde field names, IPC and
  plugin command names, event names, Android intent actions, preference keys, notification
  channels, work names and on-disk file and folder names keep their current spelling (through
  `#[serde(rename)]` where the Rust name changes): stored data, paired devices and older clients
  read them. Changing one of them is a migration in its own spec (holetz/eclume#245, #246).
- A new user-visible server message is either a problem `code` (localized by the client) or English
  text; never a new Portuguese literal.
- A new generation path takes a `locale` and ends its prompt with `output_language(locale)`.
- New web UI text goes through `t()` and both catalogs (see [The web app](#the-web-app)), never as
  a literal in JSX.
